# 从产品体验到设计决策：AI 产品拆解 Skill 的解释与注释

一份产品拆解对设计决策有用，关键在于把观察到的行为、对机制的解释和准备采取的动作连接起来。例如“支持局部修改”只是功能描述；继续追问修改后保留什么、用户要重复输入什么、是否重新计费、哪些任务因此更省事，才开始形成可以用于设计的判断。

`ai-product-teardown` 围绕这条关系组织研究：**观察证据 → 用户问题 → 设计机制 → 适用条件 → 收益与代价 → 验证方法**。本文解释它怎样工作，以及关键规则为什么这样写。文中的情境示例均为假设，没有被包装为真实产品的测试结论。

## 一、为什么把功能与交互放在第一位

入口文件明确了分析顺序：

```text
功能与交互 > 产品定位 > 技术架构 > 商业策略
```

**注释：这是研究投入的优先级，不是删减其他层的开关。** 市场、商业和技术依然需要分析，但它们应帮助解释功能边界和交互选择。例如按次收费可能影响是否提供局部重试；生成不可预测可能影响过程反馈和人工确认。报告不能花大半篇幅介绍行业，再对实际使用路径一笔带过。

有自身产品背景时，建议应回答具体问题。若用户正在设计商品视频工具，报告就应该结合该任务讨论修改粒度、角色一致性和交付衔接。没有背景时照常完成拆解，但写成有条件的借鉴，而不是替用户假定目标市场。

## 二、主流程为什么先体验、再讨论定位

默认主线是：

```text
产品介绍 → 场景体验与评测 → 差异化定位
→ 六层拆解 → 架构总结 → 设计启发
```

**注释：产品介绍负责提出假设，体验负责检验假设。** 官网可以告诉我们产品希望交付什么；真实任务则揭示用户实际拿到什么，还要自行完成哪些步骤。两者之间的差距，可能直接影响对产品定位的判断。

场景需要在执行前写清输入、预期结果和验收标准。假设研究一款报告生成工具，“生成了一份文档”并不是充分标准；还可以检查关键问题是否回答、引用能否追溯、文件能否编辑，以及需要多少人工修正。先定义标准，能减少看到结果后临时降低要求的问题。

skill 默认争取完成一个核心场景和一个合适的低成本异常测试。这是研究起点，不是稳定性实验。一次成功不能证明产品总体可靠，一次失败也不能证明该能力普遍不可用。

## 三、六层拆解和五层架构图为什么同时存在

六层拆解延续主案例的研究顺序；五层架构图来自补充课件，用于把分析压缩成一张整体图。它们承担不同任务，关系如下：

| 六层拆解的研究内容 | 五层架构中的落点 |
|---|---|
| 市场层：用户任务、替代方案、竞争切口 | 用户需求场景的依据与旁注 |
| 商业层：买单者、收费、成本约束 | 用户需求场景、模型层及商业旁注 |
| 场景与用户层：功能、使用路径和异常处理 | 用户层 |
| 技术层：执行机制、人机分工和状态恢复 | 技术层 |
| 模型层：各步骤模型与可见消耗 | 模型层 |
| 基础层：数据、权限、接口和经验沉淀 | 基础层 |

**注释：这里不是机械的一对一映射。** 商业信息可能影响多个设计层，最终图表应保留真正影响任务完成的关系。已在体验章节解释的步骤可以引用，不需要在每一层重复描述。

## 四、如何观察正向路径和异常路径

正向路径用五个环节组织：**入口、输入、过程、输出、交付**。它们分别对应用户如何找到能力、提供材料、理解执行、验收结果，以及将结果用于真实工作。

异常覆盖则检查四类问题：

| 异常 | 需要观察的设计问题 |
|---|---|
| 信息不足 | 是追问、提供示例，还是带着错误假设继续？ |
| 执行失败 | 是否解释原因，输入和进度是否保留，能否重试？ |
| 中途改意 | 能否暂停、取消、调整；已完成结果能否复用？ |
| 对结果不满意 | 能否局部修改、回退、比较版本；是否重复消耗额度？ |

**注释：检查覆盖不等于每类都必须实际制造一次故障。** 未测试项可以通过官方文档补充，也可以保留未知，但必须标明来源性质。为了凑测试数量反复生成、耗尽额度，并不能让报告更可靠。

对设计决策尤其有价值的是“修改成本”：用户发现问题后，需要重新解释多少信息、重新等待多久，以及哪些已完成工作会失效。这往往比按钮数量更能解释产品是否适合反复共创的任务。

## 五、证据三分法怎样约束结论

skill 要求重要结论使用三类标记：

```text
【页面事实】 【合理推断】 【尚未确认】
```

**注释：标记表达结论的证据状态，不是在结论末尾贴一个可靠性标签。** 每类都需要具体内容：事实要能定位来源，推断要列依据和理由，未知要说明缺口与补证方法。

假设官网写“支持团队长期记忆”：

- 可以确认的页面事实是：官方公开声明提供这项能力。
- 若跨会话任务实际复用了先前设定，可以记录这次观察，但仍需限定账号和测试条件。
- 是否采用独立向量库、多久更新、哪些数据持久化，若没有公开资料或直接证据，应保留为未知。

这也解释了为什么报告要区分亲测、官方演示和第三方评测。三者都能提供信息，但它们能支持的结论不同。证据 ID 把结论连接到原文或截图，方便以后复查和更新。

## 六、技术为什么只拆到架构与机制

关键单元的拆解维度包括：输入输出、任务、工具、上下文与记忆、规则与权限、状态和失败恢复。它们足以帮助理解执行方式和人机边界。

**注释：默认不推导内部 Schema、接口定义或系统提示词草案，是为了遵守已经选择的分析深度。** 外部行为通常不足以还原唯一的内部实现。需要实现参考时，可以在后续明确扩展任务，但不能将设计草案称为原产品的真实代码或提示词。

同理，界面上有几个角色名称，并不能证明后台存在几个独立 Agent。判断的关键是下一步如何决定：预设步骤更接近 Workflow，依据运行结果动态选择动作更接近 Agent；同一产品可能混合使用多种方式。

人机分工表还应说明为什么需要人，例如主观偏好、成本或责任，以及错误是否能够恢复。确认点的数量不是越多越好，应结合任务风险和使用负担解释。

## 七、评分和成本为什么需要单独约束

评分只适用于有标准、有观察依据的维度。报告可以评价结果是否满足要求、修改是否方便、交付是否完整；不能仅凭视频流畅就给“多 Agent 同步准确率”打分。

**注释：表格的精确外观不能替代测量。** 需要打分时，量尺、权重、扣分依据和测试样本必须一致；没有评估的维度不能悄悄补满，也不能把局部分数当成完整总评。

成本则要拆开三个概念：用户实际支付、任务可见扣点、产品供应商内部成本。一个任务扣了多少积分，不代表可以直接换算成底层模型开销。没有兑换规则或用量依据时，保留原始单位和未知项，比给出一个漂亮的估算数字更有用。

## 八、自主执行遇到阻碍时怎样处理

默认在可核实的免费额度内完成体验。需要用户协助登录、购买或使用付费额度时，暂停对应操作，继续能够独立完成的研究。

**注释：暂停的是受阻操作，不是整个报告。** 已有证据与分析要保留，交付时说明哪些内容没有亲测，以及这些缺口会影响哪些判断。用户后续补充条件后，才需要补做对应测试。

这条规则允许 skill 自主推进，也避免用公开文案填补体验空白。能否真正完成产品操作仍取决于当次环境和账号条件，skill 文件本身不会提供登录权限或额外额度。

## 九、从发现写成可执行建议

一项建议至少需要说明：证据是什么、解决谁的问题、适用什么任务、付出什么代价，以及怎样验证。

假设观察到某产品只允许整份重新生成，提出“增加局部修改”仍然不够。可以进一步形成这样的研究假设：

> 对需要多轮微调的任务，局部修改可能减少重复输入和等待。可以先支持一个明确模块的修改，检查其他模块是否保留、整体一致性是否下降，并比较完成同类任务所需的操作与人工修正。

**注释：这是待验证的建议，不是已经证明会提高留存或转化的结论。** 有自身产品背景时，还要考虑该功能的实现成本与用户使用频率；没有背景时，应保留适用条件。

## 十、文件怎么维护，当前验证到哪一步

| 文件 | 负责的内容 | 什么情况下修改 |
|---|---|---|
| `SKILL.md` | 触发范围、目标、主流程、执行与交付边界 | 工作目标或默认行为发生变化 |
| `references/research-and-testing.md` | 场景、截图、来源、评测、人机和成本细则 | 真实研究暴露取证或判断问题 |
| `references/report-template.md` | 报告结构、表格和交付自检 | 输出结构影响阅读或设计决策 |
| `agents/openai.yaml` | 展示名称、简介、示例调用 | 技能定位或调用方式变化 |
| `README.md` 与本文 | 安装使用、方法解释与维护注释 | 使用说明需要同步更新 |

运行入口只在需要时读取参考文件，本文不增加新的执行步骤。维护时优先修正真实使用暴露的问题，不要把每个偶发失败都扩展成所有任务必须遵守的新规则。

当前已检查技能格式、YAML 和本地文档引用。**尚无真实产品端到端试跑结果**，因此还不能据此评价报告质量或浏览器操作成功率。首次试跑最值得观察三件事：能否独立完成一条真实路径，结论能否回到证据，以及建议能否支持一个具体设计选择。
