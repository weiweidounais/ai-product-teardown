# 报告模板与验收

以下是默认报告骨架。按实际产品与材料调整小节，保留主线和重要未知项；不为填满模板编造内容。市场与商业写到足以解释设计选择即可，将主要篇幅留给真实体验、功能与交互。

## 报告骨架

```markdown
# 产品名：AI 产品拆解

研究日期、产品 URL、端/版本、账号档位、实际体验范围。
研究目标；若有自身产品背景，说明要支持的设计决策。

## 关键设计判断

提炼最影响决策的发现。每项给证据、判断和设计含义。
标明报告是完整亲测、部分亲测还是公开资料分析。

## 一、产品介绍

一句话说明给谁、在什么场景、解决什么问题、交付什么结果。
B 端区分使用者、买单者、验收者。
核心功能、任务边界、相关限制。

## 二、效果体验：用真实场景测试

### 场景与验收标准
用户、任务、输入材料、预期交付、测试条件、选择理由。

### 过程与结果
原始输入与关键操作，编号截图与图注。
实际成品、验收结果、耗时、人工干预、可见额度消耗。
用户旅程表或图；将每一步与证据关联。

### 异常覆盖
信息不足 / 失败 / 中途改意 / 不满意。
逐项写明已亲测、资料披露、未测试或不适用。

### 评测结论
按产品特点选择可观察维度，列标准、表现、证据。
若适合评分，列量尺、权重、得分、样本和计算方法。
证据不足时用定性评测，不给貌似精确的总分。

## 三、产品定位与差异化

替代的原有工作流程、目标用户收益、留下的人工工作。
与直接替代方案的关键差异，注明是否亲测及资料日期。
解释差异如何影响功能边界、控制感、交付与用户选择。

## 四、分层拆解

### 1. 市场层
目标任务、替代方案、竞争切口，与设计选择有关的市场条件。

### 2. 商业层
付费者、收费单位、权益、成本约束、壁垒假设与依据。

### 3. 场景与用户层
功能模块与任务对应关系。
正向五步与异常处理，重点分析引导、反馈、确认、修改和交付。
每个关键设计解释问题、机制、效果或局限；引用体验部分而非重复流水账。

### 4. 技术层
原有人工作业与人机分工表、确认点及原因。
Chatbot / Workflow / Agent / 多 Agent 的判断与证据。
关键单元输入输出、任务、工具、上下文与记忆、规则、状态与恢复。
技术流程图，明确哪些连线或机制是推断。

### 5. 模型层
步骤、模态、模型档位、自研/外接、可替换性、证据。
用户支付、可见扣点与内部成本估算分别呈现；未知处保留未知。

### 6. 基础层
数据、权限、接口、知识、资产、组织上下文、经验与积累机制。
判断可替代性及壁垒，说明依据和限制。

## 五、架构总结

五层架构：用户需求场景 → 用户层 → 技术层 → 模型层 → 基础层。
市场与商业作为前置依据或旁注，重要节点标证据类别和 ID。
解释与前文体验相互对应的关键关系，以及尚未确认的机制。

## 六、设计启发与决策建议

以功能与交互为优先，按用户背景给出具体建议。
区分事实发现、机制推断与建议，避免把个人偏好写成效果证明。
每项写适用条件、收益、代价及验证方案。

## 七、证据索引与待补测项

来源 ID、类型、标题、URL或文件、日期/版本、支持范围。
未体验的功能、缺失证据、对结论的影响、补测方法。
保留研究限制，不把未证实结论包装成已验证事实。
```

## 推荐表格

### 用户旅程

| 阶段 | 用户动作 | 产品反馈 | 用户决策/确认点 | 阻碍与修改成本 | 证据 |
|---|---|---|---|---|---|

按入口、输入、过程、输出、交付组织，允许每阶段多个步骤。确认点不存在时如实填写。图表要反映真实路径，不能将理想设计当作产品现状。

### 设计建议

| 优先级 | 发现与证据 | 设计机制 | 建议 | 适用条件 | 收益与代价 | 验证方法 |
|---|---|---|---|---|---|---|

有自身产品背景时，用其目标、资源和约束排序；没有时按潜在价值、证据强度和验证成本给条件式优先级。建议需要连接实际发现，例如：若用户需要频繁修改局部，局部重试可能降低成本；验证是否同时保留未修改部分、减少耗时且不引入不一致。不能直接宣称该设计必然提升留存或转化。

## 图表要求

- 用 Mermaid 表达流程、架构和必要的关系，用表格表达旅程和分工；不需要生成装饰性图片。
- 简单产品可以合并相近图表，但仍须回答用户如何完成任务、系统如何执行、人在何处介入。
- 标签短而具体，框内以模块名为主；对含特殊字符的标签使用引号。不要在技术图中虚构内部数据库或未公开的服务。
- 推断节点或连线显式写“推断”，图下注明事实/推断/未知的图例和证据 ID；排版样式不能替代文字说明。
- 保存 Markdown 源码；若环境具备 Mermaid 渲染能力则预览并修复语法，否则说明未进行图形渲染验证，不声称已验证。
- 截图按采集顺序命名，图注对应来源索引。链接只指向真实存在的文件；缺失证据直接写未采集。

## 交付前自检

1. **用途与主次**：功能、路径、确认点和异常处理是否是重点？是否真正给出设计决策依据？
2. **流程与覆盖**：产品介绍、场景体验、定位、六层拆解、架构总结、设计启发是否完整或说明缺口？是否适配产品类别？
3. **体验真实性**：测试条件、原始输入、结果及验收是否对应？是否把未亲测、官方演示、第三方记录分开？
4. **证据准确性**：关键结论能否定位原文或截图？声明、观察、推断、未知是否区分？时效性信息是否核查？
5. **技术深度**：是否止于架构与机制？是否凭角色名就断言多 Agent，或凭表现猜具体模型？
6. **评分与成本**：是否存在无依据评分、权重与表格不一致、总分计算错误、积分货币换算或成本混淆？
7. **建议可用性**：是否写明适用条件、代价和可执行的验证方法？有自身产品背景时是否据此判断？
8. **产物完整性**：截图路径和来源链接是否可定位，报告是否已保存，图表是否标清推断，未完成范围是否披露？

检查发现问题就修正；无法补齐时保留清楚的限制。不要为通过检查伪造测试、截图、来源或成功结果。
