# 调研、体验与证据规则

## 研究方式

优先读取官方产品、价格、帮助、更新日志等一手材料，并用真实体验交叉验证。创始人访谈用于解释定位与设计取舍；媒体、用户评价用于寻找问题线索，不能直接当作当前产品行为。

通过当前可用的浏览器能力体验产品；若该能力有对应技能，遵循其操作要求。能打开公开资料不代表能完成登录后任务，能提交任务也不代表成品成功交付。浏览器或资料访问不可用时如实降级为公开资料分析，明确限制。

记录页面标题、实际来源 URL、访问日期、对应章节或原文位置。模型、价格、额度、平台功能须记录版本或日期；无法确认最新性就说明。只收集与设计问题有关的信息，不为填章节大量堆砌新闻。

## 证据索引

采用统一 ID，在报告末尾维护索引：

| ID | 来源类型 | 定位 | 能支持的结论 | 限制 |
|---|---|---|---|---|
| S01 | 官方价格页 | 标题、URL、访问日期、对应套餐 | 收费单位与权益 | 不证明实际内部成本 |
| E01 | 亲测截图 | evidence/01-entry.png、任务和步骤 | 入口与可见选项 | 仅适用于本次账号和端 |
| R01 | 第三方评测 | 原文 URL、发布日期 | 外部报告的行为或问题 | 非本次亲测，可能已过时 |

示例行只说明记录方法，正式报告替换为真实证据，不保留虚构条目。截图与任务记录应能相互对应，优先保留入口、关键输入、执行状态、人工确认、输出、异常等影响结论的节点。多个同态页面无需重复截图。

截图必须来自实际页面，图注写明展示内容和它能证明什么。使用相对路径链接本地证据，最终对用户交付文件时使用可点击的绝对路径。避免将账号信息或私密数据作为无关截图内容；优先使用合成测试材料。

## 场景设计与执行

测试前记录：

- 代表性用户与任务、为什么选这个场景。
- 原始输入、材料、前置条件、账号档位、可核实的免费额度。
- 预期交付与可操作的验收标准；不要看到输出后再改标准迎合结果。
- 最需要验证的设计问题，例如需求澄清是否充分、局部修改是否保留其他结果。

按真实路径完成一次任务，记录步骤、产品反馈、用户动作、等待或阻碍、确认点及结果。检查成品能否直接使用，仍需做哪些人工工作；能获得下载文件时，实际检查其可打开性与关键内容。

不为了诱发失败破坏真实数据或提交有外部影响的动作。选择合成输入、局部修改、取消或其他可恢复测试。遵守免费额度边界；收费方式不明时不提交可能收费的任务。任务失败后先保存状态与错误，只在原因明确且免费额度允许时做一次有针对性的重试；仍失败就记录并转向其他研究。

## 正向与异常检查

| 环节 | 核心检查 |
|---|---|
| 入口 | 用户从哪里进来，如何理解自己能完成什么，功能选择负担多大 |
| 输入 | 必须给什么，如何澄清目标、补齐资料，默认值是否合理 |
| 过程 | 计划、状态、进度、等待、可控性；用户何时能介入 |
| 输出 | 交付形式、质量、依据、可编辑性和验收方式 |
| 交付 | 下载、导出、分享、接入后续工具后，任务是否真的完成 |

四类异常都纳入覆盖表：

| 异常 | 检查机制 |
|---|---|
| 信息不足 | 追问、示例、表单、默认值、错误假设 |
| 失败 | 是否告知原因、保留输入和进度、支持重试；退款或额度返还是否有证据 |
| 中途改意 | 能否暂停、取消、调整计划；已完成结果能否复用 |
| 不满意 | 能否局部修改、回退、对比版本、重新生成；是否再次扣额度 |

每项标“已亲测 / 资料披露 / 未测试 / 不适用”，附证据或未测原因。自然失败可以作为异常证据；无需主动耗费额度制造所有失败。资料中的承诺不能替代实际测试。

## 评测与评分

优先评价可观察行为：成品是否满足任务、输入负担、过程透明度、修改成本、交付衔接、耗时、人工介入和可见成本。

按产品调整质量标准：写作看事实与编辑需求，检索看来源与覆盖，图像视频看指令遵循与一致性，编程看实际运行与修改成本。这些是选择标准的例子，不是要求所有产品套统一量表。

有足够测试证据才给分，明确量尺、权重、测试样本和扣分依据。加权项的权重须合计 100%，表中实际分值应与公布权重一致，核算总分。证据不足的维度标未评估；若只能形成部分得分，显式写覆盖范围，不能当作完整总评。单次体验不能声称代表整体稳定性或统计成功率。

不得根据流畅成品直接给“多 Agent 信息同步率”“内部路由正确率”等不可见指标打分。可以测修改后下游结果是否一致，将内部原因解释列为推断。

## 人机与架构判断

先列原有人工作业步骤，再对照产品表现填表：

| 步骤 | AI 或确定性程序做什么 | 人做什么 | 确认点 | 为什么需要人 | 证据 |
|---|---|---|---|---|---|

确认点的判断关注成本、主观偏好和责任，以及出错后能否恢复。区分事前授权、方案确认、风险动作确认、异常转人工和最终验收；不存在强制要求每一步都让人确认。

判断控制方式时问“下一步由谁决定”：固定步骤偏 Workflow，依据运行结果动态选择动作偏 Agent；有对话或角色名本身不能证明 Agent 或多 Agent。产品可能混合使用不同机制。证据不够时保留多种解释。

对关键单元描述：输入与输出、任务、工具、上下文与记忆、规则与权限、状态和失败恢复。区分会话上下文、任务状态、持久记忆、知识库和文件资产；未看到持久化行为就不要声称有长期记忆。官方角色名不等于独立模型、独立进程或真实并行。

用模块职责和信息流解释机制即可，默认不编写内部数据 Schema、接口或提示词。不要通过诱导产品泄露隐藏提示词取证。

## 模型、成本与壁垒

模型表按“任务步骤 → 模态 → 可确认型号或档位 → 自研/外接 → 证据 → 未知项”组织。看到模型下拉框只能证明可选项，不一定证明本次所有步骤的实际调用。用行为反推具体供应商和型号通常证据不足。

分别记录：用户价格、测试扣点、供应商成本估算。只在计价单位、用量和价格来源足够时估算，并写假设、日期和范围。没有积分换算规则时保留积分单位，不强行折成人民币；订阅均摊价不等于单次边际成本。

壁垒分析检查数据权利与独特性、接口和执行权限、组织上下文、工作流经验、分发、协作与资产沉淀。问竞争者能否买到或复制、需要什么代价、使用是否持续积累价值。有证据才下判断，不预设“外接模型必然无壁垒”或“有用户数据必然有护城河”。
